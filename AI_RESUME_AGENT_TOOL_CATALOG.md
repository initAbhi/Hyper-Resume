## 1. Tool Governance & Security Invariants

### 1.1 Invariant 1: Authenticated Identity Enforcement
Under **no circumstances** may any tool accept or respect a `userId` argument generated by the AI model.
- Every tool receives a `ToolExecutionContext` populated exclusively by the backend authentication layer (`JwtAuthGuard` -> `CurrentUser`).
- If an LLM attempts to pass a `userId` parameter in its tool arguments, the tool validator strips or rejects it immediately.
- All database queries and service calls are parameterized strictly with `context.userId`.

### 1.2 Invariant 2: Tenant & Resource Ownership Verification
Before reading or mutating any resource (`resumeId`, `jobDescriptionId`, `applicationId`, `coverLetterId`), the tool must verify that the target entity belongs to `context.userId`. Attempts to access resources belonging to other tenants throw `NotFoundException` or `ForbiddenException` and immediately abort the task.

### 1.3 Invariant 3: Four-Tier Permission Matrix

```
+-------------------------------------------------------------------------------------------------+
| TIER             | BEHAVIOR                              | HUMAN APPROVAL? | DEFAULT CREDIT COST|
+-------------------------------------------------------------------------------------------------+
| READ_ONLY        | Pure inspection / retrieval           | No              | 0 credits          |
| AI_ANALYSIS      | Generative reasoning & computation    | No (preflight)  | 1 - 2 credits      |
| SAFE_MUTATING    | Additive, non-destructive creation    | No (Safe add)   | 0 credits          |
| STATE_MUTATING   | Overwrites / rolls back core data     | YES (Mandatory) | 0 credits          |
+-------------------------------------------------------------------------------------------------+
```
